## First failure: mention admission

Post `2099195064731779093` contained `@ARCIndex10 @TheArgosBot buy $10 of $ARCX10`. X retrieved it, but the application treated the multi-participant reply prefix as passive mentions. `explicitReplyRequest` returned false before a command record existed.

The user authorized manual execution. The operator removed only the unrelated leading participant from the persisted command, retaining the original post ID, author, parent, amount and ticker. This used the ordinary X command/website execution infrastructure and its transaction IDs.

The mention fix admits complete wallet commands and explicit self-wallet requests after multiple leading handles. It still requires the bot's literal current-post tag. Negation, examples, conditions, narration and posts without a bot tag are covered by regression tests; ordinary execution and ownership checks remain in place. The fix was deployed to the existing Convex backend.

## Second failure: provider availability reported as no route

ARCX10 is an Argus V4 launch with a directly verified canonical USDC pool:

- Token: `0x12ce1f970722ca6e08364b60099b3d25c09b5434`.
- Portal: `0xa5628a11c412596e1f63b75a2c0284f843c549d6`.
- Hook: `0x462b30e1d11455440eeec627bc5e30b84b18e044`.
- Pool ID: `0x778029e36cae80284b8395eb524d166bb54ccd46461918b379c21ea018db2a64`.
- Fee 10000, tick spacing 200.

At block 20,689,570, a direct 10 USDC quote returned approximately 58,207 ARCX10. The later successful guarded swap proves this was executable with this wallet. This was not an unsupported intermediary or an undiscovered hook.

The reproduction captured Argus RPC HTTP 502 / `upstream unreachable` on contract reads, Infura `project ID exceeded quota` responses, and Arc Scan connection resets from the operator machine. The original failed website request did not retain individual RPC diagnostics, so the precise failed original call cannot be identified retrospectively. The reproduced provider failures and successful direct quote establish that the blanket liquidity error was unreliable.

`quoteRoutes` previously caught provider errors and returned zero quotes. `quoteArcTrade` then reported `No supported liquid Arc route found.` as a definite preparation failure. After the two approvals completed, that stopped the request before a swap existed.

Fixes:

- Prefer working providers, then retry transient read failures once with the same block and parameters. Do not retry broadcasts, quota errors or contract reverts in this mechanism.
- When all quotes fail because of RPC availability, throw a safe retryable error rather than returning an apparent lack of liquidity. Retain a valid alternative quote if another candidate succeeds.
- Preserve chain, checkpoint, freshness, router identity, allowance, slippage, simulation and delivery checks.

With these fixes, a full preview reached the swap stage despite multiple reproduced 502 responses. It took about 19.8 seconds and 81 RPC requests. The manual continuation reused the original transaction IDs and approvals. The previously failed request was explicitly reauthorized under the user's instruction only after verifying that the prepared swap had not started signing. The swap was then signed, submitted and verified.
